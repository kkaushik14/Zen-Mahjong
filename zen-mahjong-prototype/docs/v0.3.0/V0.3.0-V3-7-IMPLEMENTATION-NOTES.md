# v0.3.0 V3-7 Persistence and Migration Implementation Notes

## Scope

Milestone V3-7 implements one versioned offline aggregate for the active Concentration run, foreground timing, assist inventory, append-only economy ledger, automatic achievement receipts, level receipts, tier progress, legacy migration archive, and future synchronization outbox.

This is a new v0.3.0 implementation record. Earlier-version documents remain unchanged. V3-7 does not implement a server, authentication, cloud conflict resolution, production synchronization, or presentation-layer adoption of the v0.3.0 run.

## Storage authority

The key `offline-state:v0.3.0` stores one validated document. A critical transition writes the entire aggregate rather than independently updating inventory, the tray, timing, and progression. This prevents a restored save from containing only half of one accepted game operation.

Each stored document contains:

- A schema version, monotonically increasing local revision, and update timestamp.
- The active run, including tray state, timing, assist usage, processed transaction IDs, and Undo snapshots.
- The append-only economy ledger from which current inventory, Concentration Score, and achievement grants are derived.
- Sequential completion receipts, tier awards, lifetime Concentration Score, and device-date streak state.
- A versioned future-sync outbox.
- An optional read-only archive of the source v0.2.0 payload.

## Commit and recovery behavior

- Every write validates the complete next payload before touching storage.
- A caller may supply the expected revision. A stale writer receives a revision conflict instead of replacing newer state.
- Before a new current document is written, the last valid current document is copied to the `:previous` key.
- If the current JSON is malformed, has a future schema, fails migration, or violates a domain invariant, reading falls back to the previous valid snapshot.
- If neither snapshot is valid, `readOrCreate` writes a validated initial v0.3.0 aggregate with the one-time initial assist grant.
- The previous snapshot is a recovery point, not an independent source of truth.

MMKV performs the physical key writes. Domain consistency comes from storing one aggregate and accepting only complete validated documents.

## Legacy v0.2.0 migration

The v0.2.0 keys remain untouched. On the first v0.3.0 hydration, the application creates the new version-specific key and follows these rules:

1. A valid legacy active session becomes a v0.3.0 Concentration run at level 1.
2. The legacy board, removed tiles, session ID, start timestamp, Hint count, and Shuffle count are preserved.
3. The migrated timer is paused with zero reconstructed active milliseconds. Wall-clock time between the old save and migration is not treated as gameplay.
4. The v0.2.0 direct-match history cannot become v0.3.0 transactional Undo history because before-and-after tray snapshots and economy transaction IDs did not exist. The migrated run therefore starts with an empty v0.3.0 Undo history.
5. The v0.2.0 player payload is archived as JSON. It is not converted into synthetic Zen Score, tier receipts, ledger entries, achievements, or streak rewards because those values cannot be derived reliably from the legacy counters.
6. The v0.3.0 economy starts with the confirmed one-time grant of 2 Shuffle, 4 Undo, and 6 Hint. Legacy prototype assist counters were usage counters, not a reliable finite balance.

These rules preserve source data without inventing progression. A later reviewed migration may consume the archive, but must use a new schema migration rather than editing this v1 document contract.

## Why MMKV and JSON, not SQLite

The current offline state is one bounded player aggregate that is replaced atomically and validated as a whole. MMKV with versioned JSON is appropriate because it provides synchronous local reads, simple backup snapshots, and direct portability to the planned synchronization payloads without maintaining relational projections.

SQLite is not needed for v0.3.0. It should be reconsidered if production requirements introduce large queryable event histories, partial record updates, cross-profile storage, content indexes, reporting queries, or retention volumes that make rewriting the bounded aggregate inefficient. If adopted, the reason and migration must be documented in a later version-specific record.

## Future-sync outbox

The outbox is a local contract only. It supports versioned, idempotent event IDs for session snapshots, economy transactions, completion receipts, tier awards, and streak visits.

- Enqueueing an existing event ID has no additional effect.
- Pending events remain durable with the same aggregate ID, occurrence time, payload version, and JSON payload.
- A future adapter may mark an event acknowledged with an explicit timestamp.
- No event is sent, retried, deleted, or trusted as server-authoritative in V3-7.
- Authentication, ordering across devices, merge policy, signature or receipt verification, retention, and server acknowledgement semantics remain backend work.

## Cross-document invariants

The restored aggregate is rejected unless:

- The active run is on the current incremental level.
- Every active-run economy transaction reference exists in the saved ledger.
- Ledger entry and transaction IDs are unique and balances remain non-negative.
- Completion receipts are sequential and unique.
- Tier awards cover exact eight-level groups and sum to lifetime Concentration Score.
- Outbox event IDs are unique and acknowledged events have acknowledgement timestamps.
- Every nested schema and game session passes its own validator.

## V3-7 assumptions and boundaries

- One local player aggregate is active at a time.
- Profile and authentication data remain outside this gameplay aggregate.
- Tutorial and practice persistence will use separate non-numbered state in V3-8 and will not create numbered completion receipts.
- The current v0.2.0 screens continue using their original repository until V3-8 connects the presentation layer to the v0.3.0 aggregate.
- The outbox may grow until a future synchronization policy defines acknowledgement retention or compaction.
- Local JSON is a durable gameplay source while offline, but it is not a substitute for encrypted credential storage.

## Verification

- Initial aggregate validation and exactly-once initial assist grant.
- Increasing revisions, stale-writer rejection, and atomic aggregate update.
- Recovery from malformed current JSON using the previous valid snapshot.
- Safe default creation when neither snapshot is valid.
- Legacy board migration with removed tiles preserved and timing paused.
- Legacy player-state archive without fabricated progression or rewards.
- Future-sync enqueue idempotency, pending selection, and acknowledgement.
- Rejection when the active level and progression disagree or run economy references are missing.
