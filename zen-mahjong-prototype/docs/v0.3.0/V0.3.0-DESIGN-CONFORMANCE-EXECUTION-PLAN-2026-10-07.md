# v0.3.0 Design-Conformance Execution Plan

Date: 2026-10-07 (Asia/Kolkata)

## 1. Purpose

This document plans the implementation of the approved Moonlit Garden V3 visual system in the existing Zen Mahjong `v0.3.0` Expo application.

This is a design-conformance and production-hardening pass. It does not restart the repository, replace the existing game engine, or repeat completed milestones V3-1 through V3-10. New work continues as V3-11 onward so historical implementation and QA records remain accurate.

## 3. Source-of-truth precedence

When sources disagree, use this order:

1. Approved game rules, economy rules, and explicit product decisions determine behavior.
2. The frozen Figma baseline determines approved visual composition and screen inventory.
3. The current framework-independent engine and persistence contracts determine technical state transitions.
4. Figma fixture values are examples only and must be replaced by real application state.
5. Missing or contradictory behavior requires a recorded decision; implementation must not invent a rule or screen.

## 4. Scope

### Included

- Moonlit Garden visual foundations, fonts, backgrounds, controls, surfaces, tiles, trays, and popup treatment.
- The 26 retained screen/state frames in the frozen design baseline.
- Real application state, persistence, accessibility, Reduced Motion, and responsive behavior behind those visuals.
- Integration of the approved 50-theme tile plan into the catalogue and artwork pipeline after asset review.
- Phone validation at 360 x 800, 390 x 844, 412 x 915, and 430 x 932.
- Preservation of the existing functional tablet layout until a separate tablet design is approved.
- iOS and Android testing, offline behavior, migration, performance, and release QA.

### Excluded

- Backend services, OAuth, cloud synchronization, account recovery, server retention, and remote configuration.
- Production advertisement SDK integration or server-side ad verification.
- In-app purchases, a Zen Token store, subscription screens, or a functional currency-purchase action.
- New tabs, bottom navigation, login, shops, marketing pages, themes, or routes not represented by approved design and product decisions.
- Rebuilding the game engine, replacing MMKV persistence, or moving rules into React components.
- Editing the Figma file or rerunning historical Figma builder scripts.

## 7. Pre-implementation decision gates

These gates do not block foundational work, but the affected interactions cannot be declared complete until resolved.

| Gate                               | Conflict or missing decision                                                              | Required resolution                                                                                |
| ---------------------------------- | ----------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------- |
| D-01 Tutorial and Practice         | Required by rules, but absent from the 26-frame V3 baseline                               | Preserve existing functional presentation, or approve/export dedicated V3 frames before reskinning |
| D-02 Daily Challenge               | Visible on Home, but a complete destination and final behavior are not established        | Confirm route, reward impact, persistence, and whether it is practice-only                         |
| D-03 Journey                       | Visible on Home, but no Journey-detail frame exists                                       | Confirm whether it is informational, navigational, or noninteractive in v0.3.0                     |
| D-04 Lotus balance and plus button | Figma shows a balance and `+`; economy mapping and purchase flow are not approved         | Map display to an approved balance and keep purchase unavailable until a store is approved         |
| D-05 Audio settings                | Music, ambient sound, and sound effects appear in Figma; audio content remains undecided  | Confirm whether v0.3.0 persists preferences only or includes a real audio implementation           |
| D-06 Daily reminder                | Settings contains a reminder toggle; permission and scheduling behavior are not specified | Define local-notification behavior before requesting system permission                             |
| D-07 No Moves wording              | Figma says no available pairs remain; game rules reject a generic no-pair failure rule    | Bind the overlay only to a valid engine state and update copy only with approval                   |
| D-08 Popup artwork readiness       | 113 source crops are reference-grade and background removal was deferred                  | Approve clean runtime assets or identify which popups can be composed without those crops          |
| D-09 Fonts                         | Four font families/styles appear in the baseline                                          | Confirm licensing, bundling files, fallback behavior, and Android rendering                        |
| D-10 Tablet composition            | Product criteria require tablet support; Figma approves phone compositions only           | Preserve current adaptive tablet behavior and request separate visual approval later               |

Each decision must be recorded in a new dated addendum or implementation note. Existing documents must not be rewritten silently.

## 8. Milestone plan

## V3-11: Baseline Lock and Implementation Matrix

### Work

- Revalidate the frozen archive checksum and manifest.
- Map all 26 approved node IDs to current routes, feature modules, reusable components, engine states, and persistence fields.
- Classify every exported image as runtime-ready, composable, reference-only, or blocked.
- Record the 10 decision gates above with owners and affected milestones.
- Remove no files and change no behavior during this milestone.
- Record stale suffixed source files such as `gameplay-screen 2.tsx`, `achievements-screen 2.tsx`, and `streaks-screen 2.tsx` for controlled cleanup after confirming they are unused.

### Deliverables

- Screen-to-code matrix.
- Asset-readiness manifest.
- Design/behavior conflict register.
- Initial runtime screenshot test matrix.

### Exit criteria

- Every approved frame has exactly one implementation target.
- Every public route is classified as approved, preserved-without-reskin, internal-only, or blocked by a design decision.
- No reference-grade crop is mislabeled as a production asset.

## V3-12: Foundations, Fonts, and Runtime Asset Pipeline

### Work

- Translate the approved Figma variables into existing design-token contracts rather than adding screen-local constants.
- Add verified font assets and load them through Expo Font using SDK 57-compatible APIs.
- Establish fallback fonts so loading or missing-font states do not shift layout unexpectedly.
- Create a stable runtime asset map containing Figma node ID, source hash, crop data, pixel dimensions, aspect ratio, readiness, and runtime destination.
- Preload critical Home, Loading, and Gameplay assets with Expo Image.
- Define responsive safe-area, phone-width, and image-crop helpers.
- Define semantic motion durations and Reduced Motion alternatives.

### Primary modules

- `packages/design-tokens`
- `apps/mobile/assets`
- `apps/mobile/src/app/_layout.tsx`
- New presentation-only asset registry under `apps/mobile/src/theme/` or `apps/mobile/src/assets/`

### Exit criteria

- Fonts are licensed, bundled, loaded, and verified on iOS and Android.
- No screen requires a hardcoded Figma image hash or absolute local export path.
- Critical assets render without stretching, checkerboards, source captions, or obvious halos.
- Foundation tests and TypeScript checks pass.

## V3-21: Visual, Accessibility, Device, and Release QA

### Interaction and accessibility gates

### Device and performance gates

- iOS simulator plus a physical iPhone 11 or newer on iOS 16+.
- OnePlus Nord 2 5G on Android 13 / OxygenOS 13.
- 36-, 72-, and 144-tile board interaction.
- Offline launch, resume, background timing, force-quit restoration, corruption fallback, and migration.
- Launch, resume, FPS, memory, battery, thermal, and repeated-level growth targets from the acceptance criteria.
- Development and preview EAS builds, followed by a documented release-candidate build.

### Exit criteria

- Every required gate is `PASS` or has an explicit approved exception.
- The final report names implemented Figma nodes, tested devices and viewports, actual command results, approved deviations, and remaining production blockers.
- The release is not called production-ready while reference-grade assets, unapproved interactions, or physical-device gates remain unresolved.

## 10. Implementation discipline

- Work one milestone at a time and create a new implementation-note document for each milestone.
- Before each edit, inspect current files and protect unrelated user changes.
- Use `apply_patch` for manual edits and the repository's existing formatters for mechanical changes.
- Add dependencies only when the current Expo SDK 57 documentation confirms compatibility and the existing stack cannot satisfy the requirement.
- Do not edit generated `ios/` or `android/` projects by hand.
- Do not start a later screen milestone while shared foundations it depends on are unstable.
- Do not mark a milestone complete from static screenshots alone; verify behavior, state restoration, accessibility, and relevant device gates.
- Keep servers stopped after verification unless the user is actively testing.
