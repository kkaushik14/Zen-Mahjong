# v0.3.0 Tile Catalogue Specification

## Purpose

One machine-readable catalogue must drive the engine, UI, accessibility labels, content tooling, tests, and the final human-readable master tile sheet.

## Required tile-design fields

```text
designId
displayName
familyId
matchIdentity
kind: regular | special
motifAsset
compactMotifAsset
accessibilityLabel
visualTags
similarityGroup
colorIndependentMarker
introducedAtLevel
eligibleCategories
contentVersion
status: draft | approved | retired
```

Every placed tile also receives a unique instance ID and board position. Instance IDs are session data and do not belong to the design catalogue.

## Matching contract

- Two instances match only when `matchIdentity` is equal.
- Similar-looking designs use the same `similarityGroup` but different `matchIdentity` values.
- UI styling, display names, or colors never determine matching at runtime.
- Retired designs remain readable for restored historical sessions.

## Special tile reuse

- Begin with an approved pool of eight special tile designs.
- A Special Concentration level selects four designs from the eligible pool.
- Later Special Concentration levels may reuse prior designs but should not repeat the exact prior four-design set when another valid set is available.
- Selection uses a deterministic seeded generator derived from level number, tier, content version, and board seed.
- The selected set is stored in level content so offline and future server execution reproduce the same result.

## Master sheet output

The generated master sheet must show:

- Artwork and compact motif.
- Stable design and match IDs.
- Display and accessibility names.
- Regular or special classification.
- Matching counterpart examples.
- Similar nonmatching examples.
- First-use and eligible-level metadata.
- Approval and content-version status.

The master sheet is a generated review artifact. It must not become a second manually maintained source of truth.
