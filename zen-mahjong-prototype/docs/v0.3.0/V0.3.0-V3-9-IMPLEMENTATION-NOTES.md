# v0.3.0 V3-9 Advertisement Adapter Implementation Notes

## Scope

Milestone V3-9 adds a provider-neutral rewarded-advertisement contract, deterministic fake provider, durable local receipts, assist rewards, advertisement-funded revival, Zen Score qualification, future-sync events, and provider-unavailable presentation behavior.

This is a new v0.3.0 implementation record. Earlier-version documents remain unchanged. V3-9 does not select a production advertisement SDK, approve production placements, implement consent policy, enforce cooldowns or daily limits, or claim fraud-resistant verification.

## Provider port

The framework-independent `AdvertisementProvider` exposes two operations:

- Query availability for an assist-reward or revival placement.
- Show a requested rewarded advertisement and return a typed result.

A result is either completed or not completed. Not-completed reasons distinguish cancellation, provider failure, provider unavailability, and unverified completion. Only a completed result whose request ID matches the original request can enter the reward pipeline.

The mobile application currently exports a deterministic fake provider. It can be configured as available or unavailable and can cycle through completed, cancelled, and failed outcomes. Completed fake impressions are explicitly marked `development`; they do not represent production verification.

## Assist advertisement reward

The development reward sheet lets the tester choose Hint, Undo, or Shuffle. A completed result:

1. Creates one durable advertisement receipt.
2. Appends exactly `+1` of the selected assist to the local economy ledger.
3. Marks the receipt as qualifying for `+1` Zen Score in the active level.
4. Adds one future-sync advertisement-receipt event.

There is no domain maximum on qualifying assist-ad receipts. Completion counts every qualifying receipt for the session and supplies that count to the existing Zen Score calculation.

Cancelled, failed, unavailable, mismatched, and duplicate results grant no inventory and no score qualification.

## Advertisement revival

When a board is failed and the provider is available, the recovery sheet offers advertisement-funded revival alongside Restart and score-funded Revive. A completed result:

1. Executes the dedicated `revive-with-advertisement` Concentration command.
2. Returns unresolved tray tiles to the board.
3. Increments the session revival sequence.
4. Spends no Concentration Score.
5. Adds no Zen Score bonus.
6. Persists the gameplay transition, receipt, and outbox event in one offline aggregate commit.

If the result is not completed or the session is no longer recoverable, no receipt is committed and Restart remains available.

## Receipt and duplicate prevention

The offline save schema advances from `1` to `2`. The migration adds an empty versioned advertisement state and preserves every existing v0.3.0 gameplay, ledger, progression, timing, legacy archive, and outbox field.

Each committed receipt stores:

- Stable receipt, request, and impression IDs.
- Session ID and placement.
- Completed timestamp.
- Development or verified classification.
- Exact reward type.
- Whether the result qualifies for Zen Score.

Receipt, request, and impression IDs must each be unique. Replaying one completed impression has no additional effect. Every assist receipt must have its matching append-only ledger transaction, otherwise the complete offline aggregate is rejected during validation.

This is local retry and reload protection, not production fraud prevention. A production adapter must obtain server-verifiable evidence and the backend must decide whether a receipt can affect synchronized account state.

## Unavailable behavior

- Provider availability is checked before advertisement actions are presented.
- Assist reward controls are absent when unavailable.
- Advertisement revival is absent when unavailable.
- Hint, Shuffle, Undo, Restart, score-funded Revive, progression, and all offline gameplay continue independently.
- Provider cancellation or failure returns the player to the same valid gameplay state.

## V3-9 assumptions

The following remain implementation assumptions because the production advertisement questions are still open:

- A completed assist advertisement grants exactly one tester-selected assist.
- Every successfully granted assist advertisement qualifies for exactly `+1` Zen Score in that active level.
- The development assist entry appears in the gameplay header and revival appears only on a failed board.
- There are no development cooldowns or daily limits, matching the confirmed unlimited score-bonus direction.
- Fake development verification is accepted only by local prototype logic and must never be treated as production account authority.

Production placement approval, age and consent handling, regional privacy behavior, cooldowns, caps, SDK lifecycle, impression verification, and server reconciliation remain release blockers for a production advertisement build.

## Verification

- Deterministic completed fake result.
- Configured cancellation, failure, and unavailable results.
- Exactly-once assist ledger grant and qualifying score count.
- Duplicate impression, receipt, and request rejection.
- Revival without Concentration Score spending or Zen Score bonus.
- Schema-one offline save migration to schema two.
- Advertisement receipt validation and ledger cross-reference.
- Future-sync advertisement receipt creation.
- Provider-unavailable gameplay remains complete and Restart remains available.
